Works fine on the synthetic test series but a real, noisier series might fit better with a different order. Flag if forecast quality looks off once real disbursement history accumulates — swapping in `auto_arima` later is a contained change (`forecasting/services.py::_fit_and_forecast`).
  - **3-month forecast horizon** is a hardcoded default (`FORECAST_HORIZON_MONTHS`), not specified by the docx ("monthly forecast" without a stated horizon length).

- Module 12 simplifications (not explicitly confirmed with client — like Module 11, the Manual has zero AHP/WSM/DSS content, this whole module is purely the docx's own spec):
  - **The 6-criterion set (`CRITERIA_METRIC_CHOICES`) is a reasonable default the client hasn't confirmed** — output volume, compliance completeness, budget utilization %, monitoring health, renewal eligibility, forecast overrun-risk (inverse). The docx says "converts institutional data into ranked, criteria-based... funding recommendations" but never names the actual criteria to use. Flag this to the client early — the whole point of AHP is that the criteria *and* their relative importance are a policy decision, not something to leave as an engineering default long-term.
  - **AHP weight computation uses the eigenvector-approximation method** (normalize columns, average rows), not the exact principal-eigenvector (power iteration/`numpy.linalg.eig`) — standard textbook approximation, accurate enough for small criteria counts (this module expects single digits), but flag if a panel member questions why weights don't match hand-computed results out past ~3 decimal places.
  - **`compliance_score` and `overrun_risk_inverse` return a neutral 0.5** when a project has no `EthicsReviewReference` / no successful `ForecastRun` yet, rather than 0 — meant to avoid punishing a project for a criterion nobody has evaluated yet, but it does mean an under-evaluated project scores *better* than one honestly evaluated as non-compliant. Worth revisiting once real evaluation coverage exists.
  - **Min-max normalization per candidate set** means a project's normalized score is relative to whoever else is in that particular WSM run, not an absolute scale — re-running with a different project_ids/funding_type/campus filter can change the same project's composite score even if its own underlying data didn't change. This is standard WSM behavior, not a bug, but worth explaining to VPRDE/DRD since it's not obvious from the number alone.
  - **AHP comparisons are submitted already-decided by the caller** (no guided "which is more important, A or B, by how much" wizard at the API level) — the frontend owns walking the user through the n*(n-1)/2 pairwise UI; this module just validates/stores/computes.
  - **No re-finalize path**: once `status="finalized"`, `AHPComparisonSubmitView` refuses further edits (400). To redo a weighting, the client creates a new `AHPMatrixRun` rather than mutating a finalized one — keeps every past recommendation run's cited weights permanently traceable to the exact AHP run that produced them, at the cost of no "just fix one comparison" shortcut.
  - **Sensitivity analysis only supports a single-criterion weight shift** (`?criterion=<id>&delta=<float>`, others proportionally rescaled) — not a full multi-criterion what-if or a weight-sweep/tornado chart. Simple version matching "sensitivity analysis" as a checkbox feature in the docx; flag if the client wants a richer visualization (that'd likely be a frontend chart consuming repeated calls to this endpoint rather than a backend change).

  - **`risk_level` bucketing (0 flags=low, 1-2=medium, 3+=high) is an engineering default**, not docx-specified — the docx names the 5 individual flags but never says how (or whether) to roll them into a single severity level. Flag if the client wants different bucket boundaries, or wants the raw flag list only with no synthesized level at all.
  - **Budget under-utilization is a flat "< 70% at any time" check**, not time-windowed — a brand-new project with 0% spent gets flagged immediately, same as a nearly-finished project that's underspent. The docx just says "vs. 70% threshold" with no timing qualifier, so this was kept as the literal simplest reading rather than inventing an end-date-proximity condition. Flag if the client actually wants this to only fire as a project nears completion.
  - **Deliverable slippage is "any overdue, non-done milestone exists"** — a binary trip-wire, not weighted by how overdue or how many. `overdue_count` is returned alongside the flag so the frontend can show severity if it wants to.
  - **Personnel-change-frequency threshold (≥2 changes in a trailing 12 months) is an arbitrary reasonable default** — the Manual's leader-concurrency rules (max 2 programs/3 projects) are about a different concern (individual overload), not about *frequency of turnover* as a risk signal, so there was nothing to anchor this number to.   - **`compute_risk_dashboard()` scopes to `status="active"` projects only** — completed/archived projects are excluded since early-warning doesn't apply to them anymore; the per-project `status/<id>/` endpoint has no such restriction and will compute regardless of status if called directly.
  - Like Module 10, **no row-level visibility scoping** — a Project Leader can query any project's risk status or the full institutional dashboard, not just their own. Same standing gap flagged in every module's dashboard/status-style endpoint so far.
